대형 가전 중고 거래 중개 플랫폼 및 촬영 소품 공유 플랫폼의 백엔드 아키텍처 설계와 데이터베이스 구축을 담당했습니다.

## <span class="material-symbols-outlined">article</span> 프로젝트 개요
- **기간**: 2021.09 ~ 2022.02 (약 6개월)
- **담당 역할**: 백엔드 엔지니어 (백엔드 전담, 프론트엔드 2명과 협업)
- **주요 기술**: Spring Boot, WebSocket, FCM, MySQL, AWS S3, 전자결제 모듈(KG이니시스, RTPay)

---

## <span class="material-symbols-outlined">report_problem</span> 문제 정의 및 접근 전략

### 문제 상황
대형 가전 중고 거래는 일반 택배 거래가 불가능하고 운송 비용이 높아 다음과 같은 구조적 제약이 있었습니다.
- 고액 배송 및 설치비로 인한 거래 마찰
- 대면 및 화물 배송 중 파손 책임 소재 불분명, 분쟁 중재 프로세스 부재

### 해결 방향
신뢰 기반의 거래 환경을 마련하기 위해 **에스크로(대금 예치) 결제 프로세스와 1:1 실시간 소통 채널**을 구축했습니다.
1. **상태 전이 시스템화**: `입금 대기` → `결제 완료` → `배송 중` → `배송 완료` → `구매 확정`에 이르는 주문 상태 라이프사이클을 엄격히 관리
2. **거래 채널 단일화**: 일정 조율 및 거래 증빙을 지원하는 앱 내 1:1 실시간 채팅 기능 구축

---

## <span class="material-symbols-outlined">code</span> 주요 개발 업무

### 실시간 채팅 및 알림 시스템 구축
- **WebSocket 기반 1:1 실시간 채팅**
  - WebView 기반 앱 환경에 맞춰 Spring WebSocket을 활용한 세션 관리 구현
  - `room_id` 단위 세션 격리를 통해 사용자 간 안전한 1:1 통신 환경 확보
- **FCM 기반 주문 이벤트 알림 연동**
  - Firebase Admin SDK를 연동하여 주문/배송 상태 전이 시 백엔드 이벤트 기반 푸시 알림 발송 파이프라인 구성

### 결제 시스템 검증 및 자동화 로직
- **결제 데이터 무결성 검증 (KG이니시스)**
  - 프론트엔드 결제 요청 금액의 위변조 방지를 위해, 결제 완료 전 서버 DB의 상품 가격과 결제 요청 금액을 2차 교차 검증하는 로직 적용
- **실시간 계좌이체(RTPay) 자동 매칭 및 예외 처리**
  - 무통장 입금 내역과 주문 데이터를 실시간 대조하여 자동 입금 확인 처리
  - 동명이인 또는 금액 불일치 등 예외 건 발생 시 관리자 확인 상태로 자동 전환하여 결제 오류 방지
- **Scheduler 기반 거래 자동 확정**
  - Spring Scheduler를 활용해 배송 완료 후 일정 기간 경과 시 상태를 '구매 확정'으로 자동 전이하고 정산 대상에 포함시키는 배치 프로세스 구현

### 소품 공유 서비스 DB 설계
- 서비스 확장을 고려한 3정규형 기반 ERD 설계로 데이터 중복 최소화
- AWS S3를 연동하여 고용량 소품 이미지 에셋을 안정적으로 업로드 및 서빙할 수 있는 기반 구축

## <span class="material-symbols-outlined">insights</span> 주요 학습 및 회고

#### 1. 운영 및 정산 관점을 고려한 결제 이력 설계
초기에는 주문 테이블에 최종 결제 상태와 금액 위주로 저장하도록 단순화했으나, 실제 운영 단계에서는 환불 및 고객 CS 대응을 위해 상세 트랜잭션 로그(결제 승인 시각, 승인 번호, 결제 수단 세부 정보 등)의 추적이 필수적이었습니다. 이를 계기로 거래 상태 변경 로그를 별도 이력 테이블로 분리 적재하도록 리팩터링하며, 단순 기능 구현을 넘어 운영 대응력을 고려한 데이터 설계 관점을 확립했습니다.

#### 2. 배치 스케줄러와 비동기 큐 확장에 대한 고민
Spring Scheduler를 활용해 주문 상태 전이와 입금 확인 배치를 안정적으로 구현했으나, 트래픽 증가 시 단일 인스턴스 스케줄러가 병목이 될 수 있음을 분석했습니다. 이를 보완하기 위해 향후 대량 트랜잭션 처리를 위한 분산 배치(Spring Batch) 및 메시지 큐(RabbitMQ/Kafka) 기반 이벤트 드리븐 아키텍처의 필요성을 검토하는 계기가 되었습니다.
